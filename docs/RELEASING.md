# Releasing LingoPop

Releases are GitHub releases built by `.github/workflows/release.yml` from a `v<version>` tag on `main`. The install instructions for users are in [INSTALL.md](INSTALL.md); the release workflow copies them into every release's notes.

## Steps

1. Bump the version to the same value in `Cargo.toml` (`[workspace.package]`), `app/src-tauri/tauri.conf.json` and `app/package.json`, then update `app/package-lock.json` with `npm install --package-lock-only --prefix app` and `Cargo.lock` with `cargo check --workspace`. Never add a `version` to `app/src-tauri/tauri.macos.conf.json`.
2. Run `python3 scripts/check-version.py`: it prints the version when all of them agree (CI and every release leg run it too).
3. Move the CHANGELOG `Unreleased` entries into a `## [<version>] - <date>` section. That section becomes the top of the release notes.
4. Check `release-platforms.json` (see below).
5. Merge through a PR, then push the tag `v<version>` on `main`. Never push a tag as a test: use `workflow_dispatch` to try the packaging.

## What the workflow does

| Job | Runner | Output artifact |
|---|---|---|
| `build-windows-portable` | `windows-latest` | `LingoPop-<version>-windows-x64`: `LingoPop-<version>-windows-x64-portable.exe`, `SHA256SUMS-windows-x64.txt` |
| `build-macos-arm64` | `macos-26` (arm64) | `LingoPop-<version>-macos-arm64`: `LingoPop-<version>-macos-arm64.dmg`, `.zip`, `SHA256SUMS-macos-arm64.txt`, `signing-macos-arm64.txt` |
| `build-macos-x64` | `macos-26-intel` (x64) | `LingoPop-<version>-macos-x64`: the same for x64 |
| `build-release-tools` | `ubuntu-latest` | `lingopop-release-tools`: the update signer / verifier binary (no secrets; its SHA-256 is a job output) |
| `publish-release` | `ubuntu-latest` | the GitHub release, created as a draft and published after the upload check (tag runs only) |

The two Mac legs are one matrix job (`build-macos`) with those display names. The runner labels are explicit because `macos-latest` is arm64 and moves with new images; they were checked against the [runner-images README](https://github.com/actions/runner-images) and the [GitHub-hosted runners reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) on 2026-11-05. Each leg also checks `uname -m`, so a label that changes architecture fails the leg instead of shipping a cross build.

- Every leg runs `scripts/check-version.py` (its output is captured with `tr -d '\r'`, because Python on Windows prints CRLF, and must not be empty) (with `--tag` on a tag run) and the frontend tests.
- The Windows leg builds `lingopop.exe` with `--features custom-protocol` and verifies the staged exe with `scripts/verify-release-assets.py verify`.
- Each Mac leg runs `scripts/package-macos.sh --version <version> --target <target> --out dist-release`: version check, the macOS readiness gate (`scripts/check-macos-production.sh`), `tauri build --bundles app` with the Mac override (`bundle.active` is true only there; Windows stays a portable exe), signing, the `.zip` and `.dmg`, the per-platform checksums, then the portable verifier plus native checks: the app extracted from the zip and the app copied out of the mounted dmg must have the bundle id `app.lingopop.tauri.macos`, the release version, minimum macOS 13.0, `LSUIElement`, the leg's architecture (`lipo`), deployment target 13.0 (`otool`), a valid signature with the hardened runtime, and the expected Gatekeeper result on quarantined copies (`spctl`).
- `build-release-tools` builds `crates/lingopop-release-tools` with `cargo build -p lingopop-release-tools --release --locked` in a job that holds no secret, uploads the binary and outputs its SHA-256.
- `publish-release` needs every job (a failed Mac leg means no release at all) and builds nothing itself. In this order, each step stopping the release on any error: it downloads the tool and compares its SHA-256 with the `build-release-tools` output (this only proves the file was not swapped between the jobs; it does not make the binary or its dependencies trusted); downloads all build artifacts into separate directories; runs `scripts/verify-release-assets.py prepare --require-mac-signing selfsigned`, which reads `release-platforms.json`, refuses any Mac `signing-<slug>.txt` other than `selfsigned` when the Mac assets are selected (the second check after the build leg's gate; a Windows-only release is unaffected), copies the selected assets, concatenates the per-platform manifests into one `SHA256SUMS.txt`, verifies the exact UNSIGNED asset set (names, sizes, checksums, zip Info.plist, Mach-O architecture / deployment target / signature, PE machine, dmg format; a `.minisig` here is an unexpected file) and writes the notes (CHANGELOG section + the Installation part of `docs/INSTALL.md`); signs the updatable assets (see "Update signatures"); verifies every signature cryptographically against the committed public key (`lingopop-release-tools verify --public-key const`); then `scripts/verify-release-assets.py finalize` appends the `.minisig` files to `SHA256SUMS.txt` (the asset lines stay the legs' checksums, so an asset changed after the pre-signing check is a checksum mismatch), verifies the complete signed set, including each signature's trusted-comment line, and only then runs `gh release create --draft` with every file (plus `--prerelease` when the version has a SemVer pre-release part such as `-alpha.1`). The release then holds 9 files with the Mac assets (exe, 2 dmg, 2 zip, 3 `.minisig`, `SHA256SUMS.txt`) or 3 without (exe, `exe.minisig`, `SHA256SUMS.txt`). The next step downloads the draft's files again and requires exactly the verified set, byte for byte (plus `sha256sum -c`); only then does `gh release edit --draft=false` publish it: a version with a pre-release part stays a pre-release, a plain version such as `0.2.0` is published with `--prerelease=false --latest` and becomes the repository's Latest release, which `/releases/latest` (the in-app update check, the README download links and badge) points to. GitHub's `/releases/latest` never returns a pre-release. A failure after the draft was created leaves a draft, never a public release with missing files: delete the draft (and only the draft) before re-running the job. It is the only job with `contents: write` and the only one that sees the update key.
- `workflow_dispatch` runs the three build legs and `build-release-tools` and uploads their artifacts; nothing is signed or published.

## `release-platforms.json`

`{"macosPreview": true}` attaches the macOS assets to the release. With `false` the Mac legs still build and verify, but the release (and its `SHA256SUMS.txt` and notes) has only the Windows exe. A missing or malformed file (any other key, a non-boolean value, invalid JSON) stops the publication.

## Keys, certificate and secrets (custody)

Two long-lived secrets make in-app updates work, and both are pinned in the code, so losing or replacing either one breaks updates for every installed copy.

| Secret | Holds | Used by |
|---|---|---|
| `UPDATE_SIGNING_KEY` | the minisign update secret key file | only the publish job's `Sign the update assets` step |
| `UPDATE_SIGNING_KEY_PASSWORD` | its password | the same step |
| `MACOS_SIGNING_P12` | base64 of the self-signed certificate and private key | the Mac legs on a tag run |
| `MACOS_SIGNING_P12_PASSWORD` | its password | the same |

- Keep an offline backup of the key, the `.p12` and both passwords, in a place of the owner's choosing outside the repository and outside CI. Never commit, print, paste into an issue or log any of them; a lost backup with the secrets still in GitHub is recoverable, a lost secret with no backup is not.
- **Never rotate** the update key or the certificate. The public key (`updates::UPDATE_PUBLIC_KEY`) and the certificate SHA-1 (`release-signing.json`, `updates::RELEASE_CERT_SHA1`) are compiled into every installed app. A new one means no installed copy accepts an update, and every user installs by hand (on macOS also re-granting Accessibility and Screen Recording). A rotation or a switch to Developer ID is a planned breaking change that updates the constants, `release-signing.json` and the spec in one release.
- **Tag-run rule.** A tag run whose release carries the Mac assets must be signed `selfsigned`; the Mac legs and the publish job both refuse anything else (see "macOS signing"), so a missing certificate secret stops the release instead of shipping a build that can't update. The update signing secrets exist only in the publish job.
- Releases before 0.2.1 (0.2.0 and the Previews) cannot update themselves. 0.2.1 is the first updater-capable release; users move to it by hand once, and Mac users grant the permissions one last time. 0.2.2 is the end-to-end check of the updater.

## Update signatures

The in-app updater installs only files signed with the project's minisign (Ed25519) update key: `LingoPop-<version>-windows-x64-portable.exe` and the two `LingoPop-<version>-macos-<arch>.zip` files each get a detached `<asset>.minisig` whose trusted comment is exactly `lingopop-update <asset file name>` (so an old signed asset cannot be served as a new version). The dmgs are not signed. The public key is the core constant `updates::UPDATE_PUBLIC_KEY`; the secret key file and its password are the repository secrets `UPDATE_SIGNING_KEY` and `UPDATE_SIGNING_KEY_PASSWORD`, referenced only by the publish job's `Sign the update assets` step. That step writes the key to a mode-0600 file under `$RUNNER_TEMP`, unsets the variable, signs with `lingopop-release-tools sign --key <file> --password-env UPDATE_SIGNING_KEY_PASSWORD` (the password stays in that one variable) and removes the file; an `if: always()` step removes it again whatever happened. Neither value is ever printed. **Never rotate the update key**: installed copies trust only the committed public key, so a new key means no installed copy can ever accept an update again and every user reinstalls by hand. Keep the secret key and its password in the GitHub secrets and in the owner's offline backup only; never commit, print or log them. A rotation is a deliberate, planned breaking change of the spec.

## macOS signing

- **Tag releases: `selfsigned`.** Every tag run whose release carries the Mac assets (`macosPreview: true`) is signed with ONE long-lived self-signed code-signing certificate, so the designated requirement stays `identifier "app.lingopop.tauri.macos" and certificate leaf = H"<sha1>"` from release to release and macOS keeps the Accessibility and Screen Recording grants across updates (an installed copy also refuses any in-app update that does not satisfy exactly that requirement). Repository secrets: `MACOS_SIGNING_P12` (base64 of the `.p12` holding the certificate and its private key) and `MACOS_SIGNING_P12_PASSWORD`. The SHA-1 of the certificate is pinned in the committed `release-signing.json` (`{"macosCertificateSha1": "<40 lowercase hex>"}`, equal to core `updates::RELEASE_CERT_SHA1`, checked by a core test). The script imports the `.p12` into a temporary keychain (deleted, and the keychain search list restored, by its EXIT trap), requires exactly one code-signing identity in it whose SHA-1 equals the pinned one (read with `security find-identity -p codesigning <keychain>` WITHOUT `-v`: the certificate is not trusted by the system policy, `CSSMERR_TP_NOT_TRUSTED`, so `-v` lists nothing, while codesign signs with it), signs with `codesign --force --sign <sha1> --keychain <kc> --options runtime --timestamp=none`, and checks every copy (zip, dmg, installed) for `codesign -d -r-` equal to the pinned requirement, `codesign --verify --strict --deep -R=<requirement>` and the hardened runtime. The app is not notarized, so `spctl` must REJECT it like an ad-hoc build, and users click Open Anyway once (the notes keep that paragraph, `macos-unnotarized`, but not the ad-hoc re-grant paragraph). The dmg stays unsigned. Mode rules: both secrets set = `selfsigned`, and then the six Developer ID secrets are ignored; only one of the two set fails the leg, naming the missing one. The `Require the pinned certificate on tag runs` step sets `RELEASE_TAG_RUN=1` on tag runs when `release-platforms.json` (read with `read_release_platforms`, an unreadable file fails the leg) says `macosPreview: true`; then anything but `selfsigned` fails with `tag releases must be signed with the pinned certificate`, and Developer ID is never selected. `workflow_dispatch` runs, and tag runs with `macosPreview: false`, may still be ad hoc. **Never rotate the certificate**: a new one changes the designated requirement, every installed copy refuses the update, and every user has to install by hand and grant both permissions again. Keep the `.p12` and its password in the GitHub secrets and in the owner's offline backup only; never commit, print or log them. Rotation (or a switch to Developer ID) is a deliberate, planned breaking change that updates `release-signing.json`, `RELEASE_CERT_SHA1` and the spec together.
- **Default without the secrets: ad hoc.** `codesign --sign - --options runtime --timestamp=none`. Gatekeeper blocks the first launch (users click Open Anyway, see [INSTALL.md](INSTALL.md)), and the notes include that paragraph. Each ad-hoc build has a new code identity, so after an update macOS may keep showing a permission as granted while it no longer applies: users remove LingoPop from System Settings > Privacy & Security (Accessibility, Screen Recording) and grant it again, and the login keychain may ask again for LingoPop's own key. Tell testers this in the release notes of every ad-hoc release (the template does).
- **Developer ID + notarization** (never on a tag run with the Mac assets) runs only when the two self-signed secrets are not set and ALL six Developer ID secrets are set: `APPLE_CERTIFICATE` (base64 of the `.p12`), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY` (for example `Developer ID Application: Name (TEAMID)`), `APPLE_ID`, `APPLE_PASSWORD` (an app-specific password) and `APPLE_TEAM_ID`. The script imports the certificate into a temporary keychain, signs the app with the hardened runtime and a secure timestamp, notarizes and staples the app and the dmg (`notarytool`, `stapler`), and expects `spctl` to accept both as Notarized Developer ID; the notes then omit the Gatekeeper paragraph. Some but not all of the six set fails the Mac legs (no silent downgrade to ad hoc). The values stay in GitHub secrets: the script prints only variable names, never values, and never runs with `set -x`. The certificate password and the Apple password are passed to `security import -P` and `notarytool --password` as command-line arguments, so other processes of the same user could see them in the process list while those commands run; that is accepted on GitHub's ephemeral, single-job runners (do not run the Developer ID path on a shared machine). Every `notarytool submit` must report `status: Accepted` (read from `--output-format json`); otherwise the script prints the submission's `notarytool log` and fails the leg.
- Every `spctl` check fails with a clear message when Gatekeeper assessments are disabled on the runner (`override=security disabled`), because the expected result can then not be checked.
- The installed app is `/Applications/LingoPop.app`; its data is in `~/Library/Application Support/LingoPop-Tauri`.

## Local checks

```bash
python3 scripts/check-version.py
python3 -m unittest discover -s scripts/tests
actionlint
shellcheck scripts/*.sh
bash scripts/check-macos-production.sh
python3 -m unittest discover -s scripts/tests -p 'test_package_macos_mode.py'  # mode selection, signs nothing
# macOS only, ad hoc, nothing is installed or launched (needs `npm ci --prefix app`):
bash scripts/package-macos.sh --version "$(python3 scripts/check-version.py)" --target aarch64-apple-darwin --out target/release-assets/macos-arm64
```

Before marking a release PR ready, run the workflow once with `workflow_dispatch` on the branch, download every artifact and check the executable architectures, the minimum macOS version, the checksum manifests and, for the Mac legs, `signing-<slug>.txt` (`selfsigned` when the `MACOS_SIGNING_P12` secrets are set, else `developer-id` when all six Developer ID secrets are set, else `adhoc`) and, only when it says `selfsigned`, `codesign -d -r-` of the app from the zip (the pinned requirement; an ad-hoc build has a `cdhash` requirement instead). The publish job (and so the signing) runs only on a tag.

The signing path can be tried locally with the committed TEST key (never the release key): build the tool (`cargo build -p lingopop-release-tools --release --locked`), run `prepare` on a set of artifacts, sign the names that `updatable` prints with `LP_TEST_PW=test target/release/lingopop-release-tools sign --key crates/lingopop-core/tests/fixtures/updates/test.key --password-env LP_TEST_PW ...`, verify them with `--public-key crates/lingopop-core/tests/fixtures/updates/test.pub` and run `finalize ... -- echo`. `--public-key const` must reject those signatures.
